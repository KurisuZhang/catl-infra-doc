## 引言：从“黑盒”到“白盒”的进化

在前几课中，我们学习了推理服务的调度、批处理和弹性扩缩容。然而，无论系统设计得多么精妙，生产环境中总会遇到意想不到的问题：为什么P99延迟突然飙升？为什么GPU利用率在高峰期反而下降？为什么用户的请求被中断了？



这些问题，如果没有一套完整的可观测性体系，只能靠猜测和“重启试试”来应对。在大模型推理场景中，可观测性不再是锦上添花的“Nice to Have”，而是保障SLO、优化成本和快速定位故障的“Must Have”。



根据火山引擎的实践，AI推理场景下可观测性接入时间可缩短**80%**，故障排查时间缩短**70%**，实现推理问题分钟级定位。



本课将从监控指标体系、分布式追踪、日志聚合与异常检测、性能压测与容量规划四个维度，系统讲解如何为推理服务构建完整的可观测性体系。







## 一、推理服务的监控指标体系

### 1.1 推理监控的三层架构

推理服务的监控指标体系可以分为三个层次，对应不同的观测视角：



| 层级              | 视角   | 核心问题            | 典型指标                  |
| --------------- | ---- | --------------- | --------------------- |
| **Model-Level** | 服务整体 | 业务是否满足预期？       | QPS、E2E延迟、Token吞吐     |
| **Pod-Level**   | 实例细分 | 负载是否均衡？问题在哪个实例？ | 各Pod延迟、KV Cache利用率    |
| **GPU-Level**   | 硬件资源 | GPU是否被充分利用？     | GPU利用率、显存占用、SM Active |





### 1.2 核心业务指标

**请求级指标**：



| 指标                               | 含义           | SLO参考        |
| -------------------------------- | ------------ | ------------ |
| **QPS**                          | 推理服务每秒处理的请求量 | 取决于模型规模和硬件   |
| **Request Success Rate**         | 请求成功率        | > 99.9%      |
| **TTFT (Time To First Token)**   | 首Token返回延迟   | 在线聊天：< 300ms |
| **TPOT (Time Per Output Token)** | 各Token间延迟    | 在线聊天：< 50ms  |
| **E2E Latency**                  | 请求平均处理耗时     | 取决于输出长度      |





TTFT和TPOT的数学关系为：E2E = TTFT + TPOT × (输出Token数 - 1)。



**Token级指标**：



| 指标                            | 含义                  |
| ----------------------------- | ------------------- |
| **Token Throughput**          | 推理服务输入和输出的Token吞吐速率 |
| **Token Throughput per GPU**  | 单GPU的Token吞吐速率      |
| **Request Prompt Length**     | 推理请求输入长度（平均值和分位值）   |
| **Request Generation Length** | 推理请求输出长度（平均值和分位值）   |





**KV Cache相关指标**：



| 指标                       | 含义                         |
| ------------------------ | -------------------------- |
| **KV Cache Hit Ratio**   | KV缓存命中率（启用Prefix Cache时有效） |
| **KV Cache Utilization** | KV缓存使用情况（百分比）              |
| **Scheduler State**      | 处于等待/运行/换出状态的请求数           |





### 1.3 GPU资源指标

推理服务的性能与GPU资源直接相关，需要监控以下指标：



| 指标                              | 含义                           |
| ------------------------------- | ---------------------------- |
| **GPU Utilization**             | GPU利用率的平均值                   |
| **GPU SM Active**               | Streaming Multiprocessor利用率  |
| **GPU Memory Copy Utilization** | 内存带宽利用率                      |
| **Used GPU Memory**             | GPU平均内存占用                    |
| **GPU Tensor Active**           | Tensor Core处于Active状态的平均周期分数 |





传统可观测性的三个支柱（指标、追踪、日志）对于推理服务而言仍然有效。但由于推理服务更贴近基础设施层，且涉及GPU等异构硬件，构建完整的可观测性面临独特的挑战：



* 推理业务指标若依赖引擎自身暴露（如vLLM的`/metrics`端点），需要将Pod加入Prometheus的采集目标

* GPU指标需要硬件主动暴露，若GPU被虚拟化，详细指标可能无法完整获取

* 流式输出场景下，TTFT/TPOT需要从全链路视角观测，而非只看单个节点

## 二、分布式追踪：从网关到引擎

### 2.1 为什么推理服务需要分布式追踪？

在大模型推理系统中，一个完整的请求可能经过多个组件：



```plain&#x20;text
API网关 → 请求调度器 → Prefill Worker → KV传输 → Decode Worker → 响应返回
```



传统日志方案的问题在于：每个组件独立记录日志，缺少统一的追踪标识，导致同一请求的日志分散在不同子系统中，无法串联成因果链。



常见问题包括：



* 请求从API网关接入后，按模型路由到不同副本，无法统一追踪

* 会话级上下文从一个模型迁移到另一个模型时，Trace无法关联

* 缓存命中路径与主推理路径并行执行，日志难以区分执行顺序

### 2.2 OpenTelemetry的统一追踪方案

OpenTelemetry是CNCF支持的可观测性框架，能够为推理平台提供分布式追踪（Tracing）、指标采集（Metrics）和日志注入（Logging）三类能力。



**核心设计原则**：



1. 在API接入层生成全局唯一的Trace ID和Session ID

2. 使用中间件或拦截器将Trace ID注入请求上下文

3) 在模型服务、KV缓存、调度器中通过请求头读取并写入日志

**推理请求生命周期Span设计**：



| 阶段        | Span名称                  | 描述                    |
| --------- | ----------------------- | --------------------- |
| 请求接收      | `api.request_received`  | 接收到HTTP请求，提取Header与参数 |
| 鉴权校验      | `api.token_validate`    | Token合法性、租户身份验证       |
| 请求调度      | `router.schedule_model` | 按模型类型路由到对应副本          |
| Prefill推理 | `model.prefill`         | 输入Prompt的KV Cache计算   |
| Decode推理  | `model.decode`          | 逐Token生成输出            |
| 响应返回      | `api.response_sent`     | 完整响应返回客户端             |





### 2.3 全链路追踪的实施路径

基于eBPF的全链路追踪方案可以实现**零代码侵入**的数据采集。在云原生环境中，它不仅能获得进程内部的数据，还能覆盖Linux内核乃至整个软件栈。



**eBPF方案在推理场景中的适用性**：



在计算密集型场景中，许多关键操作（如GPU内核函数调用、基于InfiniBand的高速网络通信）本身开销就很大，附加eBPF带来的额外损耗通常在**个位数百分比（1%-5%）**，完全可接受。



**日志结构化示例**：



```python
import logging
import json
from contextvars import ContextVar

trace_id_ctx: ContextVar[str] = ContextVar("trace_id", default="")

def log_with_trace(msg: str, **fields):
    trace_id = trace_id_ctx.get()
    log_entry = {
        "trace_id": trace_id,
        "message": msg,
        **fields
    }
    logging.info(json.dumps(log_entry))
```



### 2.4 日志聚合与链路关联

在容器化部署环境中，推荐使用 **Loki + Promtail** 构建日志流通道：



```plain&#x20;text
Promtail DaemonSet → 监听容器日志 → 提取JSON字段 → Loki存储 → Grafana可视化
```



通过配置 `pipeline_stages` 从JSON日志中提取 `trace_id`、`model_id` 等字段并生成Loki标签，可实现按Trace ID的毫秒级索引查询。



对于需要进行聚合分析的高性能查询场景，可引入 **ClickHouse** 构建列式日志分析引擎：



```sql
CREATE TABLE llm_logs (
    trace_id String,
    session_id String,
    model_id String,
    token_count UInt16,
    latency_ms Float32,
    cache_hit UInt8,
    timestamp DateTime
) ENGINE = MergeTree()
ORDER BY (timestamp, model_id, trace_id);
```







## 三、日志聚合与异常检测

### 3.1 推理日志的标准化

在生产环境中，推理日志需要包含足够的上下文信息以支持问题定位。推荐采用JSON行格式：



**建议字段**：



| 字段            | 说明          |
| ------------- | ----------- |
| `trace_id`    | 全局唯一请求ID    |
| `session_id`  | 会话ID（多轮对话）  |
| `model_id`    | 模型标识        |
| `pod_id`      | Pod/副本标识    |
| `token_count` | 当前请求Token数量 |
| `latency_ms`  | 推理时间（不含调度）  |
| `cache_hit`   | KV缓存是否命中    |
| `timestamp`   | 时间戳（毫秒或纳秒）  |





### 3.2 异常场景分类与排查

推理服务常见的异常场景可分为三类：



| 异常类型      | 典型表现         | 排查方向             |
| --------- | ------------ | ---------------- |
| **并发损坏类** | DP注意力机制并发错误  | 检查并行度配置参数        |
| **资源不足类** | 缓冲区溢出错误      | 分析缓冲区使用情况，优化内存分配 |
| **硬件兼容类** | 特定架构首Token错误 | 验证硬件支持列表，更新驱动版本  |





### 3.3 告警规则设计

基于SLO的告警规则应涵盖以下维度：



| 告警类型    | 触发条件示例                | 严重程度     |
| ------- | --------------------- | -------- |
| 延迟SLO违反 | P99 TTFT > 800ms持续5分钟 | Critical |
| 错误率超标   | 错误率 > 1%持续3分钟         | Critical |
| GPU资源瓶颈 | GPU利用率 > 95%持续10分钟    | Warning  |
| 缓存命中率下降 | KV Cache命中率 < 30%     | Warning  |





## 四、性能压测与容量规划

### 4.1 性能基准测试

在大规模部署前，必须对每个部署单元进行性能基准测试。目标是测量系统在负载下的**吞吐量**和**延迟**，这些数据是后续容量规划的基础。



NVIDIA的 **GenAI-Perf** 是专门针对LLM推理的基准测试工具，支持vLLM、SGLang等框架，提供TTFT、ITL、TPS、RPS等关键指标。



**延迟-吞吐量权衡曲线**：



性能测试的关键发现是：**低并发下延迟低但吞吐低，高并发下吞吐高但延迟增加**。这是推理服务的基本权衡，也是容量规划的出发点。



### 4.2 基于SLO的容量规划

容量规划的步骤：



**Step 1: 确定约束条件**



* 延迟类型和最大值（如TTFT < 250ms）

* 计划峰值请求/秒

**Step 2: 筛选可用配置** &#x20;

从性能测试数据中，排除不满足延迟SLO的配置点，在剩余选项中**选择吞吐量最高的配置**，这是最经济的选项。



**Step 3: 计算实例数量**



```plain&#x20;text
模型实例数 = 计划峰值请求 ÷ 单实例最优吞吐量
```



### 4.3 TCO（总拥有成本）估算

完整的成本估算应包含硬件和软件两部分：



| 成本项  | 说明            |
| ---- | ------------- |
| 硬件成本 | GPU服务器采购/租赁费用 |
| 托管成本 | 机房、电力、网络      |
| 软件成本 | 许可费、云服务费      |





**每百万Token成本**是行业通用的成本指标。计算公式：



```plain&#x20;text
每百万Token成本 = (年度总成本 / 年度Token处理量) × 1,000,000
```



### 4.4 容量规划的进阶方法

**Pareto最优分析**：在评估FP4、FP8、BF16等不同部署格式时，可使用Pareto前端可视化——在不影响其他指标的情况下无法改进的配置集合，帮助开发者选择最优精度。



**基于SLO的自动扩展**：在容量规划的基础上，NVIDIA Dynamo 0.4等平台提供了基于SLO的自动扩展功能，使推理团队能够在保证服务质量的同时，根据实时负载动态调整资源。







## 五、综合实战：推理服务监控配置

以下示例演示如何在Kubernetes环境中为vLLM推理服务配置完整的可观测性体系。



### 5.1 启用vLLM指标暴露

vLLM默认在`/metrics`端点暴露Prometheus格式指标：



```python
from vllm import LLM, SamplingParams

llm = LLM(
    model="meta-llama/Llama-2-7b-hf",
    enable_prefix_caching=True,   # 启用前缀缓存
    # 指标默认通过 /metrics 暴露
)
```



### 5.2 Kubernetes ServiceMonitor配置

通过ServiceMonitor将vLLM指标接入Prometheus：



```yaml
apiVersion: monitoring.coreos.com/v1
kind: ServiceMonitor
metadata:
  name: vllm-inference-monitor
  namespace: inference
spec:
  selector:
    matchLabels:
      app: vllm-inference
  endpoints:
  - port: http
    interval: 30s
    path: /metrics
    scheme: http
```



### 5.3 Grafana监控面板

vLLM项目提供了官方的Grafana仪表板配置（`grafana.json`），包含以下关键视图：



* **请求指标**：QPS、成功率、TTFT/TPOT分位值

* **Token吞吐**：输入/输出Token速率

* **KV Cache**：缓存命中率、利用率

* **GPU资源**：GPU利用率、显存占用、SM Active

### 5.4 端到端追踪集成示例

```python
from opentelemetry import trace
from opentelemetry.exporter.otlp.proto.grpc.trace_exporter import OTLPSpanExporter
from opentelemetry.sdk.trace import TracerProvider
from opentelemetry.sdk.trace.export import BatchSpanProcessor

# 配置OpenTelemetry
provider = TracerProvider()
processor = BatchSpanProcessor(OTLPSpanExporter(endpoint="http://jaeger:4317"))
provider.add_span_processor(processor)
trace.set_tracer_provider(provider)

tracer = trace.get_tracer(__name__)

def inference_with_trace(prompt: str):
    with tracer.start_as_current_span("inference_request") as span:
        span.set_attribute("prompt_length", len(prompt))
        # 执行推理
        result = llm.generate(prompt, sampling_params)
        span.set_attribute("output_length", len(result))
        return result
```

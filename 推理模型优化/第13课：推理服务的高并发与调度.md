## 引言：推理服务的“交通枢纽”难题

在前几课中，我们学习了推理引擎的算子优化、KV Cache管理和PD分离架构。这些技术解决了“单个GPU能跑多快”和“显存能装多少”的问题。然而，当推理服务从实验室走向生产环境时，面临的核心挑战发生了变化：**如何管理成千上万个并发请求，让GPU时刻满载，同时保证每个用户的延迟SLO？**



这本质上是**调度（Scheduling）** 问题。如果把GPU集群比作一个繁忙的交通枢纽，调度器就是那个决定“哪辆车走哪条道、什么时候出发、谁先谁后”的交通指挥中心。一个好的调度器能让道路吞吐最大化、每个乘客的等待时间最小化；一个糟糕的调度器则会让道路拥堵、乘客怨声载道。



本课将围绕推理服务调度的四个核心维度展开：请求调度策略、动态批处理、弹性扩缩容和SLO保障。





## 一、请求调度策略：FCFS vs. 优先级调度

### 1.1 FCFS：简单但致命的“先来先服务”

**FCFS（First-Come-First-Served，先来先服务）** 是最直观的调度策略——请求按到达顺序排队，先到的先处理。



**实现简单**：调度器维护一个FIFO队列，新请求追加到队尾，每次从队头取请求组成批次。



**致命缺陷：队头阻塞（Head-of-Line Blocking）**



在混合负载场景下，FCFS会导致严重的队头阻塞问题：



* 一个长请求（如32K Token的文档摘要）先到达，占用了大量GPU资源

* 后续的短请求（如100 Token的聊天回复）只能排队等待

* 即使短请求只需几十毫秒就能完成，也可能被阻塞数分钟

社区报告显示，当大请求阻塞队列时，TTFT可能超过**250秒**。在生产环境中，单个64K Token的请求会使后续亚秒级请求的P99延迟增加**8-12倍**，直接违反典型的SLO阈值（如P99 < 1s）。



在混合负载基准测试中，FCFS会导致系统吞吐下降**30-50%**。



### 1.2 优先级调度：让“重要的人先走”

**优先级调度**为每个请求分配一个优先级值（数字越小优先级越高），调度器优先处理高优先级请求。



**vLLM的实现**：



vLLM V1引擎已原生支持优先级调度。当调度策略设为 `priority` 时：



* 等待队列使用**最小堆（min-heap）** 管理，按优先级排序（低值优先），同优先级按到达时间（FCFS）

* 当显存不足需要抢占（Preemption）时，会优先终止**最低优先级**的运行中请求，为高优先级或新请求腾出空间

**使用方式**：



```python
from vllm import LLM, SamplingParams

llm = LLM(
    model="meta-llama/Llama-2-7b-hf",
    scheduler_config={"policy": "priority"}  # 启用优先级调度
)

# 高优先级请求（实时交互）
high_priority_output = llm.generate(
    "What is 1+1?",
    sampling_params=SamplingParams(priority=0)  # 数字越小优先级越高
)

# 低优先级请求（后台任务）
low_priority_output = llm.generate(
    "Summarize this long document...",
    sampling_params=SamplingParams(priority=10)
)
```



**典型应用场景**：



* **交互式请求（Chat/API）** ：高优先级，要求低延迟

* **批处理任务（摘要/Embedding）** ：中优先级，容忍较高延迟

* **后台任务（研究/实验）** ：低优先级，可被抢占

### 1.3 SJF：让“短作业优先”

**SJF（Shortest Job First，最短作业优先）** 是另一种重要的调度策略——优先处理预计执行时间最短的请求。vLLM社区正在积极推动SJF调度策略的落地。



**SJF的核心优势**：



* 快速完成短请求，大幅降低P99延迟

* 通过快速将Prefill请求转换为Decode状态，提升系统吞吐

* 减少队头阻塞对短请求的影响

**防止长请求饥饿**：



纯SJF可能导致长请求永远得不到处理。vLLM的SJF实现通过**将队列等待时间与作业长度共同纳入调度决策**来缓解这一问题——等待越久的长请求，优先级会逐渐提升。



### 1.4 更先进的调度策略

**SLA-Tiered Scheduling（SLA分层调度）** ：



vLLM社区提出的RFC建议引入三级SLA层：



| 层级              | 适用场景         | 调度行为       |
| --------------- | ------------ | ---------- |
| **interactive** | 实时聊天、API     | 最低延迟，优先调度  |
| **batch**（默认）   | 摘要、Embedding | 平衡吞吐与延迟    |
| **background**  | 研究、实验        | 最低优先级，可被抢占 |





调度器基于SLA层影响**队列排序、批次形成和抢占顺序**。



**Prompt-Aware Scheduling（提示感知调度）** ：



PARS通过成对排序（Pairwise Ranking）近似SJF调度，在无需预先知道请求执行时间的情况下实现类似效果。



**SLO-Aware LLM Inference（SLAI）调度器**：



SLAI使用实时测量来优先调度**即将错过TBT（Token间延迟）截止时间**的Decode请求，并根据已知的Prompt长度重新排序Prefill请求。在Mistral-7B的测试中，SLAI将中位TTFT降低了**53%**，最大服务容量提升了**26%**。







## 二、动态批处理与请求合并

### 2.1 静态批处理的局限性

最简单的批处理方式是**静态批处理（Static Batching）** ：将请求分组为固定大小的批次，每个批次处理完后返回结果。



**静态批处理的三大问题**：



1. **必须等待**：需要凑齐固定数量的请求才能开始处理

2. **短请求被长请求拖累**：批次中所有请求必须等最慢的完成

3) **GPU利用率低**：提前完成的请求释放了计算资源，但GPU仍在等待批次中其他请求完成

### 2.2 连续批处理：每步动态调度

**连续批处理（Continuous Batching）** 由Orca系统在2022年首次提出，核心思想是将调度决策从**批次级别**下沉到**单个Token级别**。



**核心机制**：调度器在每个解码步骤（每个Token生成）之前重新决定批次中包含哪些请求。



**工作流程**：



1. **请求入队**：所有请求放入内部队列，每个请求独立跟踪其状态（Prefill或Decode阶段）

2. **批次形成**：调度器检查队列，在 `max_num_seqs`（最大并发序列数）和 `max_num_batched_tokens`（单批次最大Token数）约束下选择尽可能多的请求

3) **动态更新**：一旦某个请求完成，**立即用新请求填充空位**，无需等待当前批次全部完成

**性能收益**：连续批处理使GPU计算单元的利用率从**60%提升至90%以上**。



**示例**：处理一个包含5个请求的批次时，若在第3步有新请求到达，连续批处理机制可立即将其加入批处理，而无需等待下一轮完整批处理。



### 2.3 连续批处理的实现细节

**批次形成的约束条件**：



| 参数                       | 含义           | 典型值       |
| ------------------------ | ------------ | --------- |
| `max_num_seqs`           | 单批次最大并发序列数   | 32-256    |
| `max_num_batched_tokens` | 单批次最大Token总数 | 2048-8192 |





调度器在每个步骤根据当前队列、Prompt长度和显存限制动态决定批次组成。



**Prefill与Decode的混合调度**：



新请求可以处于Prefill阶段，也可以处于Decode阶段。连续批处理允许在同一个批次中混合Prefill和Decode请求。



**Chunked Prefill（分块预填充）** ：



对于长Prompt的Prefill请求，可以将其切分为多个小块，与Decode请求混合调度，避免长Prompt独占GPU。



### 2.4 连续批处理的代码示例

**vLLM中的连续批处理**：



```python
from vllm import LLM, SamplingParams

# vLLM默认启用连续批处理，无需额外配置
llm = LLM(
    model="meta-llama/Llama-2-7b-hf",
    max_num_seqs=128,           # 单批次最大并发序列数
    max_num_batched_tokens=4096, # 单批次最大Token数
    gpu_memory_utilization=0.9,
)

# 提交多个请求，vLLM自动进行连续批处理
prompts = ["Prompt " + str(i) for i in range(1000)]
sampling_params = SamplingParams(temperature=0.8, max_tokens=100)

# 所有请求一次性提交，调度器自动管理批次
outputs = llm.generate(prompts, sampling_params)
```



**关键点**：将所有Prompt一次性传入 `generate()`，让vLLM内部调度器自动处理批处理。当请求数超过单批次容量时，vLLM会自动分多批次处理，并按输入顺序返回结果。







## 三、推理服务的弹性扩缩容

### 3.1 为什么需要弹性扩缩容？

推理服务的负载具有明显的**波动性**：



* **周期性波动**：白天流量高、夜间流量低；工作日高、周末低

* **突发流量**：产品发布、营销活动、热点事件导致流量瞬间激增

* **长尾效应**：少数请求占用大量资源（长文档处理）

如果按峰值负载配置固定数量的GPU实例：



* **资源浪费**：低峰期大量GPU闲置

* **成本高昂**：GPU是昂贵的硬件资源

**弹性扩缩容（Auto-scaling）** 的核心目标：根据实时负载动态调整推理服务实例数量，在保证SLO的前提下最小化资源成本。



### 3.2 Kubernetes原生扩缩容

**HPA（Horizontal Pod Autoscaler）** ：



Kubernetes原生的Pod水平自动扩缩容机制，基于CPU利用率、内存利用率或自定义指标触发扩缩容。



**大模型推理场景的挑战**：



大模型推理的负载与常规应用不同——单个Pod可能在**并发请求达到3时即达到显存上限**，而HPA默认的线性评估机制无法捕捉此类突变。



**解决方案**：使用**自定义指标**（如队列深度、运行请求数、GPU利用率）驱动HPA。



**KEDA（Kubernetes Event-Driven Autoscaling）** ：



KEDA是基于事件的自动扩缩容框架，支持多种外部触发器：



* **消息队列长度**（Kafka、RabbitMQ）

* **自定义Prometheus指标**（如Token使用量、队列深度）

* **HTTP请求流量**

KEDA的触发器配置示例：



```yaml
apiVersion: keda.sh/v1alpha1
kind: ScaledObject
metadata:
  name: llm-inference-scaler
spec:
  scaleTargetRef:
    name: vllm-deployment
  triggers:
  - type: prometheus
    metadata:
      serverAddress: http://prometheus:9090
      metricName: vllm_queue_depth
      threshold: "10"
      query: sum(vllm_waiting_requests)
```



### 3.3 云原生模型服务平台

**KServe**：



KServe是云原生模型服务平台，支持多种机器学习框架的部署和弹性扩缩容。KServe通过Knative服务实现**基于请求流量的自动扩缩容**，在无流量时可将Pod缩容到0。



**部署示例**：



```yaml
apiVersion: serving.kserve.io/v1beta1
kind: InferenceService
metadata:
  name: llama-7b
spec:
  predictor:
    model:
      modelFormat:
        name: vllm
      storageUri: s3://models/llama-7b
    scale:
      minReplicas: 0        # 无流量时缩容到0
      maxReplicas: 10       # 最大10个副本
      targetConcurrency: 5  # 每个Pod目标并发数
```



### 3.4 基于预测的智能扩缩容

**SageServe**（微软Office 365）：



SageServe分析了微软Office 365中**超过1000万请求/天**的LLM工作负载特征。它结合**短期请求路由**和**长期GPU VM扩缩容**，使用流量预测模型和整数线性规划（ILP）协同优化路由与资源分配。



**收益**：相比基线部署节省**25%的GPU小时**，GPU小时浪费减少**80%**，潜在月度成本节省达**250万美元**。



**NVIDIA Dynamo 0.4**：



Dynamo 0.4提供了**基于SLO的自动扩展**功能，使推理团队能够在保证服务质量的同时降低成本。



### 3.5 弹性扩缩容最佳实践

| 实践要点      | 说明                       |
| --------- | ------------------------ |
| **多指标驱动** | 结合GPU利用率、队列深度、请求延迟等多维度指标 |
| **预热机制**  | 大模型加载耗时数分钟，扩缩容需考虑预热时间    |
| **优雅缩容**  | 缩容前等待当前请求处理完成，避免中断       |
| **SLO驱动** | 以SLO达标率为核心扩缩容依据，而非简单指标阈值 |





## 四、服务级别目标（SLO）的保障

### 4.1 SLO的定义与度量

**SLO（Service Level Objective，服务级别目标）** 是服务提供商为自己设定的内部质量目标。



在第2课中，我们定义了推理场景的核心SLO指标：



| 指标             | 典型SLO（在线对话）       |
| -------------- | ----------------- |
| TTFT（首Token延迟） | P95 < 800ms       |
| TPOT（Token间延迟） | P95 < 150ms/Token |
| 可用性            | 月度 ≥ 99.9%        |





### 4.2 Goodput：比吞吐量更有意义的SLO指标

**Goodput（有效吞吐量）** 是在**满足SLO约束的前提下**系统每秒能完成的有效请求数。



```plain&#x20;text
Goodput = 在满足SLO（如TTFT P95 < 200ms 且 TPOT P95 < 50ms）的前提下，
         系统每秒能完成的有效请求数
```



Goodput比原始吞吐量（Throughput）更能反映用户体验——即使系统每秒处理1000个请求，如果其中300个超过了延迟SLO，用户依然不满意。



### 4.3 SLO保障的调度策略

**SLA-Tiered Scheduling（SLA分层调度）** ：



vLLM社区提出的RFC通过引入SLA层参数，让调度器根据请求的SLO要求差异化调度：



* **interactive**：保证低延迟，优先调度，限制批次中此类请求的数量以避免相互拖累

* **batch**：默认层级，平衡吞吐与延迟

* **background**：最低优先级，可被抢占

抢占顺序：background → batch → interactive。



**SLO感知的抢占**：



当KV Cache不足时，调度器需要决定抢占哪个请求：



1. 按优先级排序（低优先级先被抢占）

2. 按SLA层排序（background > batch > interactive）

### 4.4 SLO保障的监控与自愈

**监控指标体系**：



| 指标类型  | 示例                    |
| ----- | --------------------- |
| 延迟指标  | TTFT、TPOT的P50/P90/P99 |
| 吞吐指标  | Tokens/s、Requests/s   |
| 队列指标  | 等待队列长度、排队时间           |
| 资源指标  | GPU利用率、显存使用率          |
| SLO指标 | SLO达标率、SLO违反次数        |





**SLO自愈（Auto-Remediation）** ：



当SLO被违反时，系统自动触发修复动作：



1. **自动扩容**：增加推理实例数量

2. **模型降级**：从70B切换到13B或7B模型（牺牲精度换速度）

3) **请求降级**：将部分请求路由到更快的模型

**Dynamo 0.4** 提供了**基于SLO的自动扩展和实时可观察性**，使推理团队能够持续监控和优化SLO达标率。



### 4.5 SLO保障的代码示例

**vLLM中的SLA分层调度（RFC阶段）** ：



```python
from vllm import LLM, SamplingParams

llm = LLM(
    model="meta-llama/Llama-2-7b-hf",
    scheduler_config={
        "sla_tier_enabled": True,
        "max_interactive_batch_tokens": 2048,  # 限制交互式请求的单批次Token数
    }
)

# 交互式请求（高SLO要求）
interactive_params = SamplingParams(
    temperature=0.7,
    max_tokens=100,
    sla_tier="interactive"  # 最高优先级
)

# 批处理请求（默认SLO）
batch_params = SamplingParams(
    temperature=0.8,
    max_tokens=500,
    sla_tier="batch"  # 默认
)

# 后台请求（可被抢占）
background_params = SamplingParams(
    temperature=1.0,
    max_tokens=2000,
    sla_tier="background"  # 最低优先级
)
```



**SLO监控示例**（使用Prometheus指标）：



```python
from prometheus_client import Counter, Histogram, Gauge
import time

# 定义SLO指标
ttft_histogram = Histogram(
    'vllm_ttft_seconds',
    'Time to first token',
    buckets=[0.1, 0.2, 0.5, 1.0, 2.0, 5.0]
)

slo_violations = Counter(
    'vllm_slo_violations_total',
    'Total SLO violations',
    ['slo_type']  # ttft, tpot, e2e
)

def track_slo(request_id, ttft, tpots):
    # 记录TTFT
    ttft_histogram.observe(ttft)
    
    # 检查SLO
    if ttft > 0.8:  # TTFT SLO: < 800ms
        slo_violations.labels(slo_type='ttft').inc()
    
    # 检查TPOT SLO
    avg_tpot = sum(tpots) / len(tpots) if tpots else 0
    if avg_tpot > 0.15:  # TPOT SLO: < 150ms
        slo_violations.labels(slo_type='tpot').inc()
```

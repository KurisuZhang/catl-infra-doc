### 引言：甜蜜的工程答案背后的新挑战

混合专家（MoE）架构正在成为大模型推理的高效路线。它将一个大模型拆成很多“专家”，每个Token只激活其中一小部分——模型总参数量可以很大，但每次推理的实际计算量不会爆炸。DeepSeek-V3拥有671B总参数，但每Token仅激活37B；Mixtral 8x7B每Token只激活2个专家。对服务商来说，这几乎是一个“甜蜜的工程答案”：更大模型、更低成本、更高吞吐。



然而，MoE推理并非没有代价。它将“稠密模型的单卡放不下”问题转化为“专家如何分布、路由如何均衡”的系统难题。专家路由如果出现负载倾斜，部分GPU会成为瓶颈（straggler），其他GPU空等同步，MoE的并行优势反而变成系统短板。本课将围绕MoE推理的三大核心挑战——专家路由与负载均衡、专家并行的工程实现、典型模型的推理实践——展开讲解。







### 一、MoE推理的独特挑战：专家路由与负载均衡

#### 1.1 MoE的“分诊台”：路由机制

MoE模型的核心是**门控网络（Router/Gate）**，它像一个分诊台——每个Token来了之后，Router判断该交给哪些专家处理。正常文本有丰富语义，Token的隐藏表示比较分散，Router通常会把它们分给不同专家。



但在MoE推理系统中，路由失衡是一个严重的系统级风险。香港科技大学团队在ICML 2026上提出**RepetitionCurse**——一种针对MoE大模型服务的黑盒压力测试方法。它不需要模型权重，不需要梯度，只需要利用高度重复的输入模式，就能诱导Router把大量Token路由到同一小批专家上。



实验显示，在常见8-GPU EP部署上，RepetitionCurse可让MoE模型的TTFT增加**20%到148%**。问题的根源在于：MoE模型通常使用专家并行（EP）部署，不同GPU持有不同的完整专家。如果大量Token都被路由到同一GPU上的专家，那张GPU就会成为瓶颈，其他GPU即使没干多少活也必须等它完成才能继续同步。



#### 1.2 负载均衡：MoE推理的“阿喀琉斯之踵”

负载均衡已成为专家并行分布式推理中的关键问题。路由分布通常在专家之间呈偏斜分布，承载较轻负载专家的设备必须空闲等待最重的专家完成计算。



**为什么负载均衡如此困难？**



1. **动态性**：Token到专家的映射在推理过程中不断变化，静态策略无法适应

2. **跨层复杂性**：不同层的专家负载可能完全不同

3) **通信开销**：动态重新均衡会引入额外的通信和内存访问开销，有时反而得不偿失

针对这一挑战，学术界和工业界提出了多种方案：



| 方案              | 核心思路                   | 来源          |
| --------------- | ---------------------- | ----------- |
| **EPLB动态均衡**    | 异步专家负载均衡，实现零开销专家迁移     | vLLM        |
| **MoEoM**       | 联合计算与内存感知均衡，离线分组+在线重分配 | IEEE Xplore |
| **EasyBalance** | 跨层负载均衡，利用其他层专家作为自然冗余   | ICML 2026   |





vLLM的EPLB通过`--enable-eplb`启用，支持异步专家负载均衡，专家重分配过程不会中断正在进行的推理请求，实现“零开销迁移”。MoEoM通过离线的负载感知专家部署器（对称分组+复制高负载专家）和I/O感知的在线Token重分配器，将端到端推理延迟降低**最高16.6%**，跨GPU不均衡性降低**65-80%**。







### 二、专家并行的推理实现

#### 2.1 什么是专家并行？

专家并行（Expert Parallelism, EP）是MoE模型的专属并行策略：将不同专家网络分布在不同的计算设备上，每个设备仅持有部分专家（本地专家），通过集合通信操作（如All-to-All）在设备间分发和收集Token。



EP的核心价值在于**将专家“摊”到更多GPU上**，让每个GPU只负责一小部分专家，降低单卡显存压力，同时利用MoE的稀疏激活特性提升计算效率。



#### 2.2 vLLM中的EP实现

在vLLM中，EP通过`--enable-expert-parallel`标志启用。EP大小自动计算为：



```plain&#x20;text
EP_SIZE = TP_SIZE × SP_SIZE × CFG_SIZE × DP_SIZE
```



其中TP为张量并行大小，SP为序列并行大小，CFG为分类器引导并行大小，DP为数据并行大小。



**EP的通信模式**：EP组中Rank之间的底层通信是**All-to-All**。在解码阶段，当批次大小可能不大时，延迟成为重要考量，需要实现与CUDA Graph的兼容。



#### 2.3 TensorRT-LLM的大规模EP

TensorRT-LLM在大规模EP（large-EP）场景中面临一个核心工程挑战：NCCL的Send/Recv操作需要从CPU发起调用并指定数据大小，这会破坏CUDA Graph兼容性。为此，NVIDIA团队开发了**自定义EP通信内核**，可直接从GPU显存读取通信大小并兼容CUDA Graph，即使数据大小在不同运行中变化也不例外。



**大规模EP的部署用例**（来自NVIDIA实践）：



| 用例  | GPU数  | 每GPU专家数 | 每GPU层分配专家数 |
| --- | ----- | ------- | ---------- |
| 用例1 | 64    | 4       | 232        |
| 用例2 | 64-72 | 5       | 290        |
| 用例3 | 36    | 8       | 464        |





#### 2.4 阿里云PAI-EAS的EP+PD分离部署

阿里云PAI-EAS提供了**一键式EP+PD分离部署模板**，支持为DeepSeek-R1配置独立的Prefill和Decode并行策略：



* **Prefill实例**：`TP_SIZE=8`（高算力优先）

* **Decode实例**：`EP_SIZE=16-32`、`DP_SIZE=8`（高并发优先）

这种多维度联合优化范式将PD分离、大规模EP、计算-通信协同优化融为一体。







### 三、专家选择的负载均衡策略

#### 3.1 负载均衡的工程路径

MoE推理的负载均衡策略可分为静态和动态两类：



**静态策略**：在部署前确定专家到GPU的映射。vLLM支持通过`expert_map_record_path`记录初始专家分布映射，在后续部署中加载预先记录的映射以避免运行时重新计算分布。



**动态策略**：根据实时工作负载调整专家分布。vLLM通过`DYNAMIC_EPLB="true"`环境变量启用动态均衡，关键参数包括：



| 参数                                | 说明       | 建议值                  |
| --------------------------------- | -------- | -------------------- |
| `expert_heat_collection_interval` | 专家热度收集间隔 | 稳定负载400+，波动负载100-200 |
| `algorithm_execution_interval`    | 均衡算法执行间隔 | ≥30                  |
| `num_redundant_experts`           | 冗余专家数    | 必须与TP大小匹配            |





#### 3.2 学术前沿：跨层均衡与路由脆弱性

**EasyBalance（ICML 2026）** 提出了一个反直觉的洞察：其他层的专家可以视为“自然冗余”资源。通过跨层调度来自不同微批次的专家工作负载，EasyBalance可在不修改专家-设备映射的情况下实现即时适应，将GPU空闲时间均匀降低**超过40%**。



**RepetitionCurse（ICML 2026）** 则揭示了MoE路由的**脆弱性**：当输入出现高度重复的Token模式时，连续Token的表示会变得非常相似，Router会把它们反复送进同一批专家，导致负载分布从“33%/34%/33%”恶化为“98%/1%/1%”。这对生产服务意味着：即使输出只生成1个Token，也可能通过破坏Prefill阶段的计算效率拖慢整个服务。







### 四、典型MoE模型（DeepSeek-V3、Mixtral）的推理实践

#### 4.1 DeepSeek-V3/R1的推理优化要点

DeepSeek-V3采用MoE架构（671B总参数），其推理优化的核心挑战包括：



1. **MLA（Multi-head Latent Attention）算子优化**：飞桨框架3.0为DeepSeek-V3深度调优了MLA算子，通过多级流水线编排和精细的寄存器/共享内存分配，在Hopper架构上相比FlashMLA取得**4%-23%的性能提升**。

2. **MTP（Multi-Token Prediction）高效推理**：支持大批次下的投机解码加速。

3) **SageAttention动态量化**：针对DeepSeek模型实现Head Dim=192的Attention动态量化（INT8 Q/K + FP8 V），在64K长文输入下使首Token推理速度最大提升**37.4%**。

4) **EP+PD分离部署**：阿里云PAI-EAS提供一键式部署模板，Prefill采用TP=8，Decode采用EP=16-32。

#### 4.2 Mixtral 8x7B的推理实践

Mixtral 8x7B是MoE推理的经典模型。其推理优化的关键点：



1. **推理引擎支持**：llama.cpp在v103版本后初步支持MoE推理，Ollama需通过Modelfile显式声明`num_experts`和`expert_used`策略。

2. **负载均衡风险**：在vLLM 8-GPU EP部署上，RepetitionCurse可使Mixtral的TTFT最高增加**148%**。

3) **动态量化兼容**：支持W4A8动态量化，在vLLM Ascend后端已启用融合MC2。

#### 4.3 部署配置速查

| 模型           | 推荐配置                                 | 关键优化                |
| ------------ | ------------------------------------ | ------------------- |
| DeepSeek-R1  | EP+PD分离，Prefill TP=8，Decode EP=16-32 | MLA算子、SageAttention |
| DeepSeek-V3  | TP=8，启用EPLB                          | MTP投机解码             |
| Mixtral 8x7B | EP=8，启用动态均衡                          | W4A8量化              |

# 当单卡装不下大模型

在前几课中，我们学习了推理服务的调度、可观测性和KV Cache管理。然而，无论调度策略多么精妙、显存管理多么高效，物理定律不可改变：**单张GPU的显存和算力是有上限的**。



当模型参数量突破千亿甚至万亿级别时，单卡部署成为不可能的任务。以DeepSeek-R1为例，671B参数的MoE模型在FP8精度下仍需要数百GB显存——远超任何单卡容量。这时，**分布式推理**成为唯一的选择。



分布式推理的核心命题是：**如何将大模型拆分到多张GPU上，让它们协同工作，同时最大化吞吐、最小化通信开销？**



本讲将围绕分布式推理的四种核心并行策略展开：



* **张量并行（TP）** ：将单层权重切分到多卡，适合单节点部署

* **流水线并行（PP）** ：按层切分模型，适合跨节点部署

* **专家并行（EP）** ：MoE模型的专属并行策略

* **多机多卡通信优化**：让GPU集群高效协同

## 一、张量并行（TP）在推理中的应用

### 1.1 为什么需要张量并行？

当模型参数量超过单卡显存容量时，最简单的解决方案是**张量并行**：将每层的权重矩阵切分到多张GPU上，各卡同时计算一部分，最后通过通信聚合结果。



例如，LLaMA-3 70B模型在FP16精度下约需140GB显存——单卡A100（80GB）装不下，但2张A100（共160GB）就可以容纳。通过张量并行，模型权重被切分到2张卡上，每张卡负责一半的计算。



### 1.2 张量并行的两种基本形式

张量并行主要依赖两种技术：



**列并行（Column Parallelism）** ：将权重矩阵沿列方向切分。每个GPU计算部分输出维度，最后拼接结果。适用于QKV投影和MLP的上投影（up-projection）层。



**行并行（Row Parallelism）** ：将权重矩阵沿行方向切分。每个GPU计算部分输入维度，最后通过All-Reduce求和。适用于注意力输出投影和MLP的下投影（down-projection）层。



**Transformer层的典型TP模式**：



在一个Transformer块中，列并行和行并行配对使用：



```plain&#x20;text
输入 → [列并行QKV] → [列并行MLP上投影] → 激活函数 → [行并行MLP下投影] → 输出
                                                              ↑
                                                         All-Reduce
```



这种设计使得**每个Transformer块只需要一次All-Reduce通信**，通信开销被控制在较低水平。



### 1.3 vLLM中的张量并行配置

在vLLM中启用张量并行非常简单——通过`tensor_parallel_size`参数指定GPU数量：



```python
from vllm import LLM

# 在4张GPU上运行张量并行推理
llm = LLM(
    model="meta-llama/Llama-3-70b-hf",
    tensor_parallel_size=4,  # 使用4张GPU
)

# 服务端启动方式
# vllm serve meta-llama/Llama-3-70b-hf --tensor-parallel-size 4
```



**选择TP大小的通用原则**：



* **单节点部署**：`tensor_parallel_size` = 节点内GPU数量

* **多节点部署**：`tensor_parallel_size` = 每节点GPU数量，`pipeline_parallel_size` = 节点数量

* **边界情况**：若GPU间无NVLink（如L40S），利用流水线并行代替张量并行，可获得更高吞吐和更低通信开销

### 1.4 TP的超线性扩展效应

分布式推理中一个反直觉的现象是：**性能提升可能超过GPU数量的线性增长**。



这是因为张量并行不仅增加了算力，更关键的是**显著扩大了KV Cache容量**。更大的KV Cache允许更大的Batch Size，从而提升GPU利用率和Token吞吐。



实测数据显示，当TP从1扩展到2时，KV Cache块数量增加了13.9倍，Token吞吐提升达到3.9倍——远超2倍的线性预期。







## 二、流水线并行（PP）在推理中的适用性

### 2.1 PP的工作原理

张量并行解决了“单层权重装不下”的问题，但当模型层数过多、甚至单个节点都装不下时，就需要**流水线并行**：将模型的不同层分布到多张GPU上，每张GPU处理连续的若干层。



```plain&#x20;text
GPU 0: Layer 1-10   →   GPU 1: Layer 11-20   →   GPU 2: Layer 21-30
     (输入)          (中间激活传递)          (输出)
```



每个GPU处理完整的输入Token序列，但只经过其负责的层子集，然后将中间激活值传递给下一个GPU。



### 2.2 PP vs. TP：通信开销的权衡

| 维度   | 张量并行（TP）        | 流水线并行（PP） |
| ---- | --------------- | --------- |
| 切分粒度 | 层内（权重矩阵）        | 层间（连续层）   |
| 通信频率 | 每层多次            | 每阶段一次     |
| 通信量  | 大（All-Reduce张量） | 小（中间激活）   |
| 适用场景 | 单节点、高带宽互联       | 跨节点、低带宽互联 |





**核心取舍**：TP通信频繁但通信量可控（通过配对列/行并行每块只需一次All-Reduce）；PP通信频率低，但每个阶段的GPU需要等待前一个阶段完成，存在“流水线气泡”（Pipeline Bubble）问题。



### 2.3 vLLM中的流水线并行配置

vLLM通过`pipeline_parallel_size`参数启用流水线并行：



```bash
# 跨2个节点，每节点8张GPU，同时使用TP和PP
vllm serve meta-llama/Llama-3.1-405b-fp8 \
    --tensor-parallel-size 8 \
    --pipeline-parallel-size 2
```



**推荐配置策略**：



* 将`tensor_parallel_size`设置为每个节点中的GPU数量

* 将`pipeline_parallel_size`设置为节点数量

* 这样每个节点独立完成张量并行，节点间仅通过流水线传递激活

### 2.4 PP在推理中的特殊性

值得注意的是，流水线并行在**推理场景**中的收益不如训练场景明显。推理的Decode阶段是串行逐Token生成的，流水线的“微批次”优化（GPipe提出的Micro-batching）在推理中效果有限。因此，在生产环境中，除非模型大到单个节点装不下，通常优先选择张量并行而非流水线并行。







## 三、专家并行（EP）在MoE模型推理中的应用

### 3.1 什么是专家并行？

专家并行是专门为**混合专家（MoE）模型**设计的并行策略。它将不同的专家网络分布在不同的GPU上，每个GPU只持有并计算一部分专家（本地专家），通过All-to-All等集合通信在设备间分发和收集Token。



MoE模型的核心优势是**稀疏激活**——每个Token只激活少数专家（如DeepSeek-R1每Token激活8个专家，共256个专家）。这意味着虽然模型总参数量巨大，但每次推理的计算量只与激活专家数相关。



专家并行的本质：**把专家“摊”到更多GPU上，让每个GPU只负责一小部分专家，降低单卡显存压力，同时提升专家权重的加载效率**。



### 3.2 专家并行的通信模式

EP的核心通信操作是**All-to-All**：



1. **分发（Dispatch）** ：每个GPU根据路由结果，将Token发送到对应专家所在的GPU

2. **计算**：每个GPU在其本地专家上执行计算

3) **合并（Combine）** ：将各GPU的计算结果汇总回原始Token所属的GPU

这种通信模式在Decode阶段尤其关键——每个解码步骤都需要动态路由和Token分发，通信开销可能成为性能瓶颈。



### 3.3 大规模EP的负载均衡挑战

当EP规模超过8时，一个严重的问题浮现：**专家负载失衡**。



通过分析DeepSeek-R1在32个GPU上运行的数据，NVIDIA团队发现了以下规律：



1. **热点专家**：某些层存在少数“热门专家”，接收的Token数远超其他专家

2. **跨迭代稳定**：这种失衡在数十到数百次解码迭代中保持稳定

3) **数据集敏感**：不同数据集（机器翻译 vs. GSM8K）的热点层和热点专家不同

**失衡带来的问题**：



* 热门EP所在的GPU消耗更多显存，限制有效Batch Size

* 热门EP成为系统瓶颈，拖慢整体端到端延迟

**解决方案：在线专家负载均衡（EPLB）**



TensorRT-LLM的Wide-EP引入了在线负载均衡器：



* **统计采集**：在GPU上实时采集各专家的Token路由数据

* **复制与放置**：在CPU上运行放置算法，决定哪些专家复制到哪些GPU

* **动态权重更新**：在解码迭代间以分层方式重新分配MoE权重，不影响用户体验（分层方案每次只更新部分层，避免服务中断）

实测数据显示，在GB200 NVL72上，大型EP配置（EP=32）相比小型EP配置（EP=8），每GPU吞吐量提升**1.8倍**。



### 3.4 vLLM中的专家并行配置

在vLLM中启用专家并行：



```bash
# 启用专家并行（仅对MoE模型有效）
vllm serve deepseek-ai/DeepSeek-R1 \
    --enable-expert-parallel \
    --tensor-parallel-size 8
```



**EP大小的自动计算**：



```plain&#x20;text
EP_SIZE = TP_SIZE × SP_SIZE × CFG_SIZE × DP_SIZE
```



其中TP为张量并行度，SP为序列并行度，CFG为分类器引导并行度，DP为数据并行度。



**实际部署案例**：阿里云PAI-EAS提供了一键式EP+PD分离部署模板，支持为DeepSeek-R1配置Prefill（TP=8）和Decode（EP=16-32）的独立并行策略。







## 四、多机多卡推理的通信优化

### 4.1 通信是分布式推理的“阿喀琉斯之踵”

分布式推理的性能天花板往往不是算力，而是**通信**。当模型分布在多张GPU上时，它们需要频繁交换中间结果，通信延迟和带宽直接影响端到端推理速度。



### 4.2 NVIDIA NCCL：通信的统一抽象层

NVIDIA集合通信库（NCCL）是分布式推理的通信基础。它自动为给定拓扑选择最优传输方式，将NVLink、NVSwitch、PCIe和InfiniBand抽象化为统一接口。



**关键通信原语**：



| 原语         | 用途                              |
| ---------- | ------------------------------- |
| All-Reduce | 求和/平均所有GPU的结果（TP中行并行的核心）        |
| All-Gather | 收集所有GPU的数据（上下文并行的KV交换）          |
| All-to-All | 每个GPU向所有其他GPU发送不同数据（EP的Token分发） |





### 4.3 上下文并行（CP）：长序列的解决方案

上下文并行是TensorRT 11.0引入的新并行策略，专门针对**长序列推理**场景。



**核心思想**：将输入序列沿序列维度切分到多张GPU，每张GPU只处理序列的一部分。



**三种实现方式**：



| 策略                | 通信模式              | 适用场景       |
| ----------------- | ----------------- | ---------- |
| AllGather KV      | 每层All-Gather交换K/V | 短到中长序列     |
| Ring Attention    | 环形流式传输，计算通信重叠     | 超长序列       |
| DeepSpeed Ulysses | All-to-All按注意力头分区 | 数万Token长序列 |





在NVIDIA Cosmos3视频生成和FLUX.1图像生成的基准测试中，**Ulysses策略在超长上下文中表现最优**。



### 4.4 NVLink：让通信不再是瓶颈

GB200 NVL72机架提供了**130 TB/s的聚合NVLink带宽**，使大规模EP的通信开销大幅降低。



**关键数据**：



* NVLink域内GPU间通信延迟可控制在纳秒级

* 单机8卡A100通过NVSwitch实现全互联，带宽达600GB/s

* PCIe 4.0带宽仅32GB/s，差距近20倍

**工程建议**：



* 张量并行和专家并行应优先部署在**同一NVLink域**内的GPU上

* 跨节点通信应使用InfiniBand或RoCE高速网络

* 使用`nvidia-smi topo -m`查看GPU拓扑，合理分配任务

### 4.5 解耦服务与通信优化

NVIDIA Dynamo将PD分离与分布式推理结合，通过解耦Prefill和Decode阶段，让通信优化更加精细化：



* **Prefill阶段**：使用低TP（减少通信），专注计算

* **Decode阶段**：使用高TP/EP（提升内存带宽利用率），专注访存

* **KV传输**：通过NIXL（NVIDIA Inference Transfer Library）在P/D实例间高效传输KV Cache

实测数据显示，在GB200 NVL72上部署DeepSeek-R1时，Dynamo的PD分离+EP优化使请求吞吐量提升了**30倍**。







## 五、并行策略选择决策树

```plain&#x20;text
模型能否放入单卡？
├── 能 → 单卡推理（无需分布式）
└── 否 → 继续

模型是MoE架构吗？
├── 是 → 专家并行（EP）为核心
│   ├── 单节点 → TP + EP
│   └── 跨节点 → TP + EP + PP
│
└── 否 → 密集模型
    ├── 单节点 → 张量并行（TP）
    ├── 跨节点 → TP + PP
    └── 超长序列 → TP + 上下文并行（CP）

通信优化原则：
- TP/EP放在同一NVLink域内
- PP跨节点（通信频率低）
- 结合PD分离优化各阶段并行策略
```

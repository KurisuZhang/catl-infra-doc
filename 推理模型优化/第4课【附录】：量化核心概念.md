### 一、为什么INT8行得通？

想象你在给一座城市的**100万居民**记录身高数据（单位：米）。如果要求**绝对精确**（FP32），你需要记录 `1.753248...` 这样的小数，数据量极大且没必要。现在官方要求你改为**按“厘米”取整记录**（INT8量化）。



* **映射（量化）**：1.753米 → 175厘米。

* **反推（反量化）**：175厘米 → 1.75米（误差0.003米）。

这个“厘米”就是**缩放因子（Scale）**。虽然丢失了小数点后几位的精度，但绝大多数场景（如统计平均身高）依然准确。**神经网络比身高数据更“抗造”**，它对权重中的微小噪声有天然的鲁棒性，这就是量化可行的生物学/数学基础。



### 二、手算推演：从FP32到INT8的完整映射（对称量化 vs 非对称量化）

假设我们有一个**FP32**的权重张量：`[ -10.0,  -2.5,  0.0,  8.0 ]`，我们想把它量化为 **INT8（范围 -128 \~ 127）**。



#### 场景1：对称量化（Zero-point = 0）

我们只算缩放因子 `S`。



* 计算最大值 `max_abs = max(|-10|, |2.5|, |0|, |8|) = 10.0`。

* 为了防止溢出，`S = max_abs / 127 = 10.0 / 127 ≈ 0.07874`。

* **量化公式**：`q = round(原始值 / S)`。

  * `-10.0 / 0.07874 = -127` → q = -127

  * `-2.5 / 0.07874 ≈ -31.7` → q = -32

  * `0.0` → q = 0

  * `8.0 / 0.07874 ≈ 101.6` → q = 102

* **反推验证**（反量化）：`-32 * 0.07874 = -2.519`（原本是-2.5，误差仅0.019）。

#### 场景2：非对称量化（带零点偏移，处理激活值不对称的好手）

假设激活值全为正数：`[ 0.0,  1.2,  5.5,  10.1 ]`（范围不对称，没有负数）。



* 计算 `min_val=0.0`, `max_val=10.1`。

* 缩放因子 `S = (max - min) / 255 = 10.1 / 255 ≈ 0.0396`。

* 零点 `Z = round(0 - min / S) = 0`（这里刚好为0，但假如最小值是2，零点就会偏移）。

* **直观差异**：对称量化的范围是`[-10, 10]`，如果激活全为正数，那负数范围就完全浪费了！**非对称量化**通过零点偏移，让INT8的 `[0~255]` 完美覆盖激活值的 `[0.0 ~ 10.1]`，**有效精度提升了近一倍**。

### 三、破解“LLM量化最难痛点”：异常值（Outlier）的毁灭性打击

讲完基础，我们来看LLM真正的噩梦——**异常值**。



假设某层激活值的分布是：`[ 1.2,  1.5,  1.3,  1.4,  1.6,  300.0 ]`。 &#x20;

这个 `300.0` 就是一个巨大的异常值。



* **如果做普通的INT8量化（对称）**： &#x20;

最大绝对值=300。缩放因子 `S = 300 / 127 ≈ 2.36`。 &#x20;

当你把 `1.5` 除以 `2.36` 时，得到 `q ≈ 0.63`，量化后直接变成 `1`（或0）。 &#x20;

**后果**：绝大部分正常的激活值（1.2\~1.6）在量化后都被挤到了相邻的1\~2个整数格里，**信息完全丢失**！只有异常值占了127这个格子。

* **LLM.int8()的解法**：检测到异常值（>6.0），**不量化它**，保留为FP16；只量化正常的小数值。但这导致硬件无法使用纯INT8矩阵乘法核，影响速度。

* **SmoothQuant的精妙之处（具体数字演示）**： &#x20;

SmoothQuant说：“既然激活值里有300，那我**在它进入线性层之前，先除以一个巨大的平滑因子（比如除以100）**，让300变成3；但同时，把**权重乘以100**，保证 `激活 × 权重` 的数学结果不变！”

&#x20;   \- 原来：`[1.2, 300] * W`

&#x20;   \- 改变后：`[0.012, 3] * (W * 100)` &#x20;

此时最大值变成了3，再无异常值，所有值都能舒舒服服地用INT8精准表达！**这就是把量化难度从“难以量化的激活”迁移到了“容易量化的权重”上**。

### 四、GPTQ vs. AWQ 的“微观战场”：剪头发与戴头盔

两种主流方法在量化70B大模型时，具体的微观操作截然不同：



#### 1. GPTQ（误差补偿机制）——就像“剪头发时用推子找平”

假设一层有四个权重（极度简化）：`[0.5, 0.2, -0.1, 0.8]`。



* **粗暴量化**：四舍五入取整，可能变成 `[0, 0, 0, 1]`，误差巨大。

* **GPTQ的骚操作**：

  1. 先量化第一个权重 `0.5` → `0`（误差 +0.5）。

  2. 为了弥补这个误差，**GPTQ立刻调整后面未量化的权重**。例如，把 `0.2` 临时改为 `0.7`（补偿了-0.5）。

  3) 再去量化 `0.7` → `1`（误差 -0.3），继续向后补偿。 &#x20;

通过这种\*\*“边剪边补”的逐层递推\*\*，GPTQ让整个矩阵的最终输出误差最小化。这也是为什么GPTQ极度依赖Hessian矩阵（判断哪些权重对补偿最有效）。



#### 2. AWQ（保护1%的“重要神经元”）——就像“给关键部位戴头盔”

AWQ通过观察激活值的分布，发现**0.1%\~1%的权重处于“交通要道”**，哪怕改动0.1也会导致模型崩溃。



* 例如，`W1 = 0.02`（不重要），`W2 = 100.5`（极重要）。

* **AWQ不做误差补偿，而是直接保命**：量化时，给 `W2` 乘以一个保护缩放因子（比如放大2倍变成201），然后量化。因为放大后数值变大了，量化后的相对误差就变小了。

* 推理时，再把这部分特殊权重恢复回去。 &#x20;

**结论**：GPTQ像精细的外科手术（依赖计算），AWQ像聪明的安保策略（依赖观察激活值），在边缘端硬件上，AWQ的加速效果更直接。

### 五、真实世界的“量化选型沙盘”（含具体代码逻辑）

如果你手上有**Llama 3 8B**模型，显存只有**16GB**，必须用INT4量化。我们来看代码层发生的实际变化（基于AutoGPTQ库的伪代码逻辑）：



```python
# 伪代码：GPTQ 逐层量化的微观视角
def gptq_quantize_layer(layer, calibration_data):
    # 1. 拿到该层的权重 (FP16)
    W = layer.weight  # shape: [4096, 4096], 约 32MB
    
    # 2. 计算 Hessian 矩阵 (基于校准数据判断哪些行列重要)
    H = compute_hessian(calibration_data, layer)  # 二阶梯度信息
    
    # 3. 逐列量化 (从最后一列往前)
    for col in range(W.shape[1] - 1, -1, -1):
        # 量化这一列 (FP16 -> INT4)
        W_quant[col] = quantize(W[col])  
        
        # 核心：计算量化误差
        error = W[col] - dequantize(W_quant[col])
        
        # 如果误差>阈值，把误差按照 Hessian 逆矩阵 分摊给剩余未量化的列！
        if error > threshold:
            W[:, :col] -= error * inv_H  # 权重漂移补偿！
    return W_quant
```



**这个例子让你看到**：GPTQ根本不是一次性把所有权重四舍五入，而是**一边量化一边用数学公式（Hessian）修正后续未量化的权重**，把量化噪音强行“消化”掉。

### 六、FP8：为什么它是H100的“亲儿子”？（算一笔账）

在NVIDIA H100上，FP8比INT8快，不仅因为硬件原生支持，更因为**无需“反量化”等待**。 &#x20;

假设一个矩阵乘法：



* **INT8方案**：权重INT8，激活INT8 → 算完得到INT32 → **必须等待CUDA核把INT32转回FP16**才能给下一层（这一步有延迟）。

* **FP8方案**：权重FP8，激活FP8 → 张量核心直接算完，**输出的格式就是FP16/BF16**（Hopper架构做了格式对齐）。

**具体数字例子**： &#x20;

在H100 SXM上，处理一个Token的Decode阶段：



* INT8推理：延迟约 2.1ms。

* FP8推理：延迟约 1.5ms（**快28%**），且精度损失比INT8更小，因为FP8的指数位（E4M3）能表示更大的动态范围，不容易被异常值撑爆。

### 七、精度评估的“实战体检表”（不只是看PPL）

很多同学只会看“困惑度（PPL）”来衡量量化好坏，但在大厂实战中，这远远不够。我们以量化一个\*\*代码生成模型（如CodeLlama）\*\*为例：



| 评估维度                 | 具体例子（量化后）          | 结论                         |
| -------------------- | ------------------ | -------------------------- |
| **PPL（语言流畅度）**       | 从 5.2 升到 5.8       | 轻微变差，可接受                   |
| **HumanEval（代码通过率）** | 从 85% 掉到 62%       | **灾难性退化！** 说明量化把逻辑/符号能力破坏了 |
| **GSM8K（数学推理）**      | 从 70% 掉到 71%（反而升了） | 奇怪的现象（噪声正则化），说明该任务对量化不敏感   |
| **MT-Bench（多轮对话）**   | 从 8.5 掉到 7.2       | 表达变僵硬了                     |





**真实大厂结论**：如果只测PPL，你可能会觉得量化很成功；但一旦测**HumanEval（代码任务）**，你会发现INT4量化会导致代码生成准确率断崖式下跌（对数值符号极端敏感）。这时你必须改为**混合精度（关键层保持FP16）** 或改用**AWQ**（保护代码相关的显著权重）。

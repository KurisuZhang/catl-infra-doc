#

## 引言：软件优化跑在硬件之上

前两课我们建立了推理的指标体系——知道了要优化什么、如何度量。但所有优化策略最终都要落地到具体的硬件上执行。**软件优化决定了性能的上限能到多高，硬件选型则决定了性能的下限在哪里。**



大模型推理的硬件选型，本质上是在回答三个问题：



1. **装不装得下**：显存/内存容量能否容纳模型参数和KV Cache？

2. **跑不跑得快**：硬件带宽和算力能否满足延迟/吞吐的SLO要求？

3) **划不划得来**：单位成本下的性能产出是否满足商业诉求？

本课将从数据中心到边缘端，逐层剖析推理硬件的选型逻辑。







## 一、GPU推理 vs. CPU推理：架构差异与适用场景

### 1.1 为什么GPU成了推理的首选？

在回答"GPU还是CPU"之前，先理解一个根本问题：**为什么大模型推理离不开GPU？**



大模型每次生成一个Token，都需要读取全量的模型参数。以Llama 3 70B模型为例，FP16精度下模型权重约140GB——这远远超出了任何CPU内存总线的单次吞吐能力。传统的CPU+内存架构的算力和带宽无法满足如此恐怖的计算密度，计算和通信都必须转移到GPU内完成。



GPU的核心优势在于**大规模并行计算**和**高带宽显存（HBM）** 。现代GPU可提供数个Petaflops等级的FP8张量吞吐量，以及每秒数TB等级的高带宽内存存取能力。这种算力与带宽的组合，正是大模型推理所必需的。



### 1.2 GPU推理 vs. CPU推理：架构差异

| 维度      | GPU             | CPU          |
| ------- | --------------- | ------------ |
| 核心数量    | 数千个小型计算核心       | 数十个大型通用核心    |
| 并行能力    | 大规模SIMT并行       | 有限线程级并行      |
| 内存架构    | HBM高带宽显存（TB/s级） | DDR内存（GB/s级） |
| 适用场景    | 计算密集+访存密集       | 逻辑控制、串行任务    |
| 能效比（推理） | 高（每瓦特Token数高）   | 较低           |





GPU的架构设计天然适合大模型推理的"矩阵乘法密集"特性。但CPU也并非毫无用武之地——英特尔至强6处理器内置的**AMX（高级矩阵扩展）** 矩阵加速引擎，可加快INT8和BF16数据格式的推理速度，INT8的速度高达每核每时钟周期2,048次浮点运算。在3-13B规模、INT8/BF16量化的模型上，AMX可使CPU达到50-120 Tokens/s的吞吐。



### 1.3 适用场景：各归其位

**GPU的"主场"** ：



* **在线推理服务**：对延迟敏感的Chatbot、实时翻译、编程助手

* **大模型（70B+）部署**：模型参数远超CPU内存带宽承载能力

* **高并发场景**：需要同时处理大量请求

**CPU的"用武之地"** ：



* **离线批处理**：对时延要求不高的批量推理任务，线上保有量大的CPU可用更低成本完成任务

* **小模型推理**：3B以下的SLM（小型语言模型），CPU完全可胜任

* **GPU前置/辅助任务**：模型预处理、小参数LLM推理、RAG管道的轻量级推理

* **CPU-GPU协同推理**：通过CXL将部分计算offload到CPU，优化延迟和吞吐

值得注意的是，**CPU-GPU紧耦合架构**正在改变游戏规则。研究显示，NVIDIA GH200（Grace CPU + Hopper GPU）在大型批次下，Prefill延迟可比PCIe连接的松耦合系统快1.9-2.7倍。随着模型参数量突破万亿级别，GPU显存容量日益成为瓶颈，CPU的内存容量优势正在被重新审视。







## 二、推理场景下的GPU选型：A100/H100/L4/L40S

### 2.1 GPU选型的三个核心维度

评估一张显卡的大模型价值，逻辑极其残酷：**训练看算力（FLOPS）和NVLink，推理看显存容量和显存带宽**。



* **显存容量**：决定模型"装不装得下"。模型权重 + KV Cache + 中间激活，三者之和必须小于显存容量。

* **显存带宽**：决定Token"生成有多快"。Decode阶段每生成一个Token都需要从显存读取全部模型权重，带宽直接决定TPOT。

* **算力（FLOPS）** ：决定Prefill阶段"算得有多快"。虽然Decode阶段受带宽限制，但Prefill阶段是计算密集的。

### 2.2 四款主流推理GPU对比

| 规格   | A100          | H100       | L4           | L40S         |
| ---- | ------------- | ---------- | ------------ | ------------ |
| 架构   | Ampere        | Hopper     | Ada Lovelace | Ada Lovelace |
| 显存容量 | 40/80GB HBM2e | 80GB HBM3  | 24GB GDDR6   | 48GB GDDR6   |
| 显存带宽 | 2.0 TB/s      | 3.35 TB/s  | 300 GB/s     | 864 GB/s     |
| 定位   | 全能型（训练+推理）    | 旗舰训练+高性能推理 | 低功耗推理        | 高性价比推理       |
| 推理性能 | 基准            | 4倍于A100    | 入门级          | 中端           |





**A100（Ampere架构）** ：AI领域的"老将"。虽然已被H100超越，但在推理场景中仍是高性价比选择——提供良好的推理性能且功耗更低。适合13B-70B模型的推理部署，尤其是在成本敏感的生产环境中。



**H100（Hopper架构）** ：当前旗舰。集成800亿晶体管，支持Transformer引擎和FP8精度。适合需要最高吞吐的极端工作负载，如超大模型（70B+）的高并发在线服务。但用H100跑7B模型是"杀鸡用牛刀"，浪费了高端GPU的成本。



**L4（Ada Lovelace架构）** ：专为低功耗推理设计。24GB GDDR6显存，带宽约300GB/s。适合轻量级推理任务和小模型部署，是边缘节点和入门级推理服务的性价比之选。



**L40S（Ada Lovelace架构）** ：推理的"甜点级"选择。48GB GDDR6显存，可容纳13B-70B范围的模型。在实时推理场景（如LLM服务）中，L40S配合TensorRT优化后，延迟较H100可降低22%。适合不需要H100级算力开销的混合图形和AI工作负载。



### 2.3 选型决策树

```plain&#x20;text
模型大小？
├── < 7B → L4（成本最优）或 CPU（批处理场景）
├── 7B - 30B → L40S（性价比最优）
├── 30B - 70B → L40S（可容纳）或 A100（更高带宽）
└── > 70B → H100（性能最优）或多卡并行

并发要求？
├── 低并发 → 单卡L4/L40S
├── 中并发 → 单卡H100/A100
└── 高并发 → 多卡H100 + 张量并行

延迟SLO？
├── 宽松（>500ms）→ 可降级选型
└── 严格（<100ms）→ H100/L40S + 极致优化
```







## 三、显存带宽与计算能力的权衡

### 3.1 推理的两个阶段，两种瓶颈

大模型推理分为两个截然不同的阶段，对硬件的要求完全不同：



**Prefill阶段（上下文分析）** ：处理超长输入序列的编码。这是**计算密集型（Compute-Bound）** 任务——需要大量矩阵乘法运算，瓶颈在GPU的峰值算力（FLOPS）。H100的FP8 Tensor Core算力在此阶段大显身手。



**Decode阶段（生成任务）** ：逐Token预测输出。这是**访存密集型（Memory-Bound）** 任务——每生成一个Token都需要从显存读取一次全部激活权重参数。瓶颈在显存带宽，而非算力。



### 3.2 核心公式：Token生成速度 = 显存带宽 ÷ 模型大小

这是推理硬件选型中最重要的一条公式。



以Llama 3 70B模型（INT4量化后约35GB）为例：



* **H100**（带宽3.35TB/s）：理论最大Tokens/s = 3,350GB / 35GB ≈ 95 Tokens/s

* **L40S**（带宽864GB/s）：理论最大Tokens/s = 864GB / 35GB ≈ 24 Tokens/s

* **L4**（带宽300GB/s）：理论最大Tokens/s = 300GB / 35GB ≈ 8.5 Tokens/s

> **关键洞察**：在这个公式里，**显存容量完全没有参与计算**。只要模型能够完整装入显存，决定生成速度的是带宽而非容量。这就是为什么AMD MI455X虽然显存容量是NVIDIA Rubin的1.5倍（432GB vs. 288GB），但推理速度反而略逊——因为NVIDIA通过更高的显存频率获得了更大的带宽。
>
>



### 3.3 显存容量：决定"能装多少"

显存容量决定了三件事：



1. **模型能否完整装入**：FP16的70B模型约140GB，单卡H100（80GB）装不下，需量化或张量并行

2. **Batch Size能开多大**：每个请求的KV Cache占用显存，Batch越大，KV Cache越大

3) **上下文能有多长**：长上下文场景下，KV Cache可能远超模型权重本身

### 3.4 "内存墙"——推理优化的根本挑战

现代GPU的算力增长速度远超显存带宽增长速度。以H100为例，其FP8算力高达数个Petaflops，但HBM带宽仅3.35TB/s。在Decode阶段，算力远未被充分利用——MFU通常只有10%-30%。



这就是所谓的 **"内存墙"（Memory Wall）** ：计算单元在等待数据从显存中读取，而非在真正计算。推理优化的许多核心技术——KV Cache量化、FlashAttention、PagedAttention——本质上都是在**绕过或缓解内存墙**。



在MoE（混合专家）模型部署中，显存带宽对推理性能的影响权重可达60%，远高于单纯计算单元数量。这进一步印证了：**推理优化的首要瓶颈是带宽，而非算力**。







## 四、边缘端推理：移动端NPU与轻量化部署

### 4.1 从云端到边缘：推理的"最后一厘米"

AI正在从云走向边缘，从数据中心走向终端设备。边缘AI不再只跑人脸识别、物体检测等简单CNN模型，大语言模型正被部署到智能手表、耳机、传感器等对功耗极度敏感的设备上。



边缘端推理面临的核心约束：



* **功耗**：移动设备电池容量有限，推理必须低功耗

* **算力**：远低于数据中心GPU

* **内存**：数GB级别，远小于服务器显存

* **散热**：无主动散热，持续推理能力受限

### 4.2 NPU：边缘推理的"专用引擎"

**NPU（神经网络处理单元）** 是专为AI推理设计的专用硬件，正越来越多地集成到移动SoC中——高通的Hexagon NPU、联发科的APU、英特尔Core Ultra的NPU、AMD的XDNA NPU。



NPU相比通用CPU的核心优势：



* **专用矩阵计算单元**：针对矩阵乘法和卷积优化

* **低精度加速**：INT8/FP16等低精度推理效率极高

* **高能效比**：每瓦特可完成的推理操作数远超CPU/GPU

研究显示，在边缘端SLM推理中，NPU的性能远超通用CPU。在CNN推理中，NPU可实现CPU的5.2倍加速；在LLM推理中，NPU在Prefill阶段可实现4倍加速。结合性能和功耗的指标（如EDP，能量延迟积）来看，NPU仍然是主导架构。



安谋科技发布的"周易"X3 NPU IP，在Llama2 7B大模型实测中，Prefill阶段算力利用率高达72%。这一代NPU的FP16算力较上一代提升16倍，Softmax和LayerNorm性能提升超过10倍。



### 4.3 轻量化部署的技术栈

边缘端推理需要软硬协同的优化：



**算法层面**：



* 模型量化（INT8/FP16）

* 模型剪枝与蒸馏

* 轻量化Transformer架构（如MobileLLM）

**硬件协同层面**：



* 专用NPU与编译工具显著提升能效比

* 跨平台统一推理框架（如Nexa SDK），统一支持苹果NPU、Intel NPU、AMD NPU、高通NPU等多类NPU推理加速

**部署工具**：



* 谷歌推出Coral NPU——面向边缘AI的开源全栈平台，使LLM可嵌入到微型设备中实现全天候运行

* ONNX Runtime、TensorFlow Lite等框架的边缘端适配

### 4.4 边缘推理 vs. 云端推理：不同的优化哲学

| 维度   | 云端推理                | 边缘推理         |
| ---- | ------------------- | ------------ |
| 首要目标 | 吞吐 + 延迟             | 能效 + 隐私      |
| 硬件平台 | GPU（H100/A100/L40S） | NPU + CPU    |
| 模型规模 | 70B-万亿参数            | 1B-13B（SLM）  |
| 优化重点 | 批处理、KV Cache、量化     | 模型压缩、低精度、稀疏化 |
| 部署方式 | 集中式集群               | 分布式终端        |

## 引言：没有度量，就没有优化

"如果你无法度量它，你就无法管理它；如果你无法管理它，你就无法改进它。"这句管理学格言在大模型推理领域尤为贴切。推理优化是一个系统工程，而性能指标体系就是工程师手中的"仪表盘"——它告诉我们系统当前在什么位置、瓶颈在哪里、优化是否真正有效。



许多初入推理优化领域的工程师常犯的一个错误是：只盯着某一个指标（比如首Token延迟），却忽略了其他维度的考量。一个TTFT极低但TPOT极高的系统，用户体验依然糟糕；一个延迟完美但吞吐极低的系统，在商业化场景中同样不可行。



本课的核心目标，是帮你建立一套**多维度的推理性能评估坐标系**。我们将从三个递进的层面展开：



* **用户感知层**：TTFT、TPOT、端到端延迟——用户"体感"好不好？

* **系统效率层**：Tokens/s、Requests/s——系统资源利用是否充分？

* **商业价值层**：P99延迟、SLA/SLO、每百万Token成本——能否支撑规模化商业服务？

理解这些指标之间的关联与制约关系，是成为一名合格推理优化工程师的第一步，也是最关键的一步。







## 一、核心延迟指标：用户"体感"的量化

大模型推理的延迟并非单一维度。由于自回归生成的特性，一次完整的推理请求可以被切分为多个阶段，每个阶段都有其独立的延迟指标。



### 1.1 首Token延迟（TTFT, Time-To-First-Token）

**定义**：从客户端提交推理请求，到收到模型返回的第一个输出Token之间的时间间隔。



**覆盖阶段**：TTFT包含了请求在网络中的传输时间、服务端的排队等待时间，以及最关键的计算阶段——**Prefill阶段（预填充阶段）** 的全部计算时间。在Prefill阶段，模型需要处理用户输入的整个Prompt，一次性计算并缓存所有输入Token的KV Cache。



**用户体验映射**：TTFT直接决定了用户对AI响应速度的"第一印象"。人类对交互延迟的感知极为敏感——当TTFT超过2秒时，用户会明显感到"卡顿"；超过4秒时，交互体验将被显著破坏。在实时对话、搜索引擎等场景中，TTFT通常要求在**500ms\~2s**之间。



**影响TTFT的关键因素**：



* **Prompt长度**：输入越长，Prefill阶段的计算量越大，TTFT越高。

* **批处理策略**：若请求被调度器延迟以等待批次凑齐，TTFT会增加（这是延迟-吞吐权衡的典型体现）。

* **算力资源**：GPU算力越强，Prefill阶段的矩阵乘法完成越快。

**优化方向**：通过PD分离架构将Prefill与Decode解耦、使用FlashAttention加速Prefill计算、优化调度策略减少排队时间。



### 1.2 Token间延迟（TPOT, Time-Per-Output-Token）

**定义**：在生成阶段（Decode阶段），模型每生成一个输出Token所需的平均时间间隔。



**覆盖阶段**：TPOT覆盖的是**Decode阶段的单步推理时间**，即从第n个Token生成到第n+1个Token生成之间的时间差。在Decode阶段，模型每次只需要处理一个新生成的Token（而非全部Prompt），计算量相对较小，但需要频繁访问KV Cache。



**用户体验映射**：TPOT决定了文本生成的"流畅度"。人类阅读速度约为每秒5-10个Token，因此TPOT的理想区间在**100ms\~200ms/Token**（即每秒生成5-10个Token），这样用户才能获得流畅的阅读体验。若TPOT超过500ms/Token，生成过程将显得"一个字一个字往外蹦"，体验急剧下降。



**影响TPOT的关键因素**：



* **显存带宽**：Decode阶段是**访存密集型（Memory-Bound）** 计算，其速度高度依赖GPU的显存带宽（HBM Bandwidth）。这也是为什么A100/H100的HBM带宽（分别达2TB/s和3.35TB/s）对推理性能至关重要。

* **KV Cache大小**：上下文越长，KV Cache越大，每次需要读取的数据量越大，TPOT越高。

* **Batch Size**：批次越大，单次推理需要处理的Token越多，TPOT线性增加。

**优化方向**：KV Cache量化压缩、FlashAttention（减少显存读写）、更快的HBM（H200相较于H100）、投机解码（Speculative Decoding）。



### 1.3 端到端延迟（End-to-End Latency）

**定义**：从请求提交到完整输出全部生成内容的总时间。



**计算公式**：



```plain&#x20;text
端到端延迟 ≈ TTFT + (生成Token数 - 1) × TPOT
```



**应用场景**：端到端延迟是衡量**离线批处理**任务效率的核心指标。对于在线推理而言，用户更关注TTFT和TPOT的分别表现；但对于离线的文档总结、代码生成等任务，总完成时间才是最直接的效率度量。



**陷阱提示**：端到端延迟相同的两个系统，用户体验可能天差地别——一个TTFT=1.5s、TPOT=50ms的系统，比一个TTFT=100ms、TPOT=200ms的系统在长文本生成中体验更好，但在短文本场景中则相反。因此，**绝不能只用一个端到端延迟来评估推理系统的表现**，必须拆解。







## 二、吞吐指标：系统效率的标尺

如果说延迟指标回答的是"单个请求跑得有多快"，吞吐指标回答的则是"系统在单位时间内能干多少活"。吞吐能力直接决定了推理服务的成本效益。



### 2.1 Tokens/s（每秒生成Token数）

**定义**：系统每秒能够生成的Token总数。该指标有两种统计口径：



* **端到端吞吐**：从请求开始到结束，总生成Token数除以总耗时，包含Prefill时间。适用于评估离线批处理任务。

* **Decode阶段吞吐**：仅统计Decode阶段每秒生成的Token数。该指标更能反映系统的"稳态生成能力"，不受Prompt长度变化影响，是推理引擎性能对比的常用基准。

**与TPOT的关系**：在单请求场景下，Tokens/s ≈ 1 / TPOT（即TPOT的倒数）。但在并发场景下，系统通过批处理同时服务多个请求，整体Tokens/s可以远超单请求的1/TPOT。



**优化目标**：在线服务中，通常需要**Tokens/s ≥ 用户总需求**，否则会出现请求积压。例如，若高峰期每秒有100个并发请求，每个请求需要生成10个Token，则系统吞吐至少需要达到1000 Tokens/s。



### 2.2 Requests/s（每秒处理请求数）

**定义**：系统每秒能够完成的完整推理请求数量。



**应用场景**：



* **短文本场景**（如分类、情感分析、实体抽取）：每个请求的输入输出都很短，瓶颈在请求调度和框架开销上，Requests/s是更合适的吞吐指标。

* **批量离线任务**：如每日千万级的用户画像更新，Requests/s直接决定任务能否在窗口期内完成。

**影响因素**：Requests/s受请求复杂度影响极大——一个生成10个Token的请求和一个生成1000个Token的请求，其消耗的资源不可同日而语。因此，在报告Requests/s时，**必须标注平均输入/输出Token长度**，否则该指标毫无意义。



### 2.3 延迟与吞吐的"跷跷板"——通过Batching量化理解

延迟与吞吐的矛盾在批处理（Batching）中体现得最为直观。我们用一组简化数据来感受一下：



假设单个请求的Decode单步推理时间为10ms。当Batch Size=1时，生成100个Token的TPOT为10ms/Token，吞吐为100 Tokens/s。若将Batch Size提升至32，GPU计算单元被充分并行化，但由于需要同时处理32个请求的KV Cache读写，单步推理时间可能增加到50ms。此时：



* 单个请求的TPOT = 50ms/Token（延迟变差）

* 系统吞吐 = 32 × (1000ms / 50ms) = 640 Tokens/s（吞吐大幅提升）

延迟牺牲了5倍，但吞吐获得了6.4倍的提升。在大规模商业化部署中，这种权衡往往是"划算的"——只要TPOT仍在SLO允许的范围内（比如< 200ms/Token），就应尽量增大Batch Size以提升吞吐。



**核心口诀**：在线看延迟，离线看吞吐；动态调Batch，SLO是红线。







## 三、服务质量指标：从平均值陷阱到SLO保障

在真实的分布式生产环境中，**平均值往往是最具欺骗性的统计量**。一个系统的平均延迟可能是200ms，但如果99%的请求都在50ms内完成，而1%的请求卡了10秒，用户体验的灾难是显然的。这就是为什么要引入百分位数和服务等级协议。



### 3.1 P50/P90/P99/P999延迟

**定义**：



* **P50（中位数）** ：50%的请求延迟低于该值。代表"大多数用户"的典型体验。

* **P90**：90%的请求延迟低于该值。代表"绝大多数用户"的体验。

* **P99**：99%的请求延迟低于该值。代表"最差情况下的1%用户"的体验，也称**长尾延迟（Long-tail Latency）** 。

* **P999**：99.9%的请求延迟低于该值。对应极端异常情况。

**为什么P99如此重要？**



在大型互联网服务中，1%的用户可能意味着每天数百万人的糟糕体验。某头部云厂商的实践表明，P99延迟每升高100ms，用户次日留存率下降约0.5%。在AI推理场景中，长尾延迟可能源于：显存分配抖动、内核调度延迟、网络波动、其他租户的资源争抢等。



**关键认知**：推理优化的目标通常不是降低"平均延迟"，而是**削平P99长尾**。一个P99=2s、P50=200ms的系统，与P99=500ms、P50=300ms的系统相比，后者的用户体验一致性更好，更值得信赖。



**观测建议**：在生产环境中，延迟指标应以**滑动时间窗口**（如过去5分钟）内的百分位数进行实时统计和告警，而非单纯依赖平均值。



### 3.2 SLA（Service Level Agreement，服务等级协议）与SLO（Service Level Objective，服务等级目标）

这两个概念常被混淆，但它们的层次不同：



* **SLA**：服务提供商与客户之间的**正式合同约定**。定义了服务达不到标准时的赔偿条款（如退款、服务抵扣）。SLA通常是法律效力的文件。

* **SLO**：服务提供商为自己设定的**内部质量目标**。SLO比SLA通常更严格，为SLA留出"安全垫"。

**推理场景中的典型SLO示例**：



| 指标维度 | SLO目标（在线对话场景）     | 说明                    |
| ---- | ----------------- | --------------------- |
| TTFT | P95 < 800ms       | 95%的请求在800ms内返回首Token |
| TPOT | P95 < 150ms/Token | 95%的生成步骤间隔低于150ms     |
| 可用性  | 月度可用率 ≥ 99.9%     | 每月停机时间不超过43.2分钟       |
| 错误率  | 错误率 < 0.1%        | OOM、超时等异常占比           |





**SLO的设定原则**：



1. **业务导向**：SLO必须基于用户体验而非工程师的主观偏好。如果业务要求实时交互，TTFT的SLO就不能超过1s。

2. **留有余地**：内部SLO应比对外SLA严格20%-30%。例如，SLA承诺TTFT < 1s，内部SLO应设为TTFT < 800ms。

3) **可度量、可告警**：每个SLO都应有明确的度量方式和对应的告警规则。

4) **动态调整**：随着硬件升级和优化技术的进步，SLO应定期review和收紧。

## 四、成本指标：商业可持续性的度量

AI Infra工程师不仅要有技术视野，更要有"算账"的能力。在商业化落地中，推理成本直接决定了产品的定价策略和毛利率。



### 4.1 每百万Token成本（Cost per Million Tokens）

**定义**：处理一百万个Token（包括输入和输出）所需的计算资源成本。这是业界衡量推理服务经济性的**黄金标准**。



**计算方式**：



```plain&#x20;text
每百万Token成本 = (GPU实例小时单价 × 推理耗时小时数 × GPU数量) / 处理的Token总数 × 1,000,000
```



更实用的是**单位成本分解**：



```plain&#x20;text
总成本 = GPU采购成本分摊 + 电力成本 + 机房/运维成本
每百万Token成本 = 总成本 / 月度Token处理量
```



**行业基准（参考）** ：



* 2025年初，使用H100集群部署的Llama 3 70B模型，优化前的每百万Token成本约为0.5-1.0美元；经过量化+PD分离+连续批处理优化后，可降至0.1-0.2美元。

* DeepSeek等公司通过极致的MoE架构和推理优化，将成本压至0.014美元/千Token（即14美元/百万Token）——需注意这是输出Token的定价，且模型为MoE架构，实际算力成本会随负载变化。

**优化意义**：每百万Token成本每降低10%，在日均万亿Token调用的规模下，意味着每年数千万美元的利润释放。这也是大厂AI Infra团队不惜重金招募推理优化工程师的根本商业逻辑。



### 4.2 算力利用率（Compute Utilization）

算力利用率从资源效率的角度衡量推理系统的健康度，主要包括两个子指标：



**（1）MFU（Model FLOPs Utilization，模型浮点运算利用率）**



**定义**：模型实际达到的计算吞吐量，相对于该GPU理论峰值算力的百分比。



```plain&#x20;text
MFU = (实际处理的Token数 × 模型单Token FLOPs) / (GPU峰值FLOPs × 运行时间)
```



**典型值**：



* 训练场景下，优秀的MFU可达50%-60%（如Megatron-Turing）。

* 推理场景下，Decode阶段由于是访存密集型，MFU通常仅有**10%-30%** 。这意味着超过70%的算力实际上"闲置"了——瓶颈在显存带宽而非计算单元。

* Prefill阶段的计算密集性使得MFU可达40%-50%。

**核心洞察**：推理优化的关键挑战在于**如何突破内存墙（Memory Wall）** ，尽可能提高Decode阶段的MFU。这也是为什么FlashAttention、KV Cache压缩等技术如此重要——它们减少了显存读写，让计算单元"等得更少"。



**（2）显存带宽利用率（HBM Bandwidth Utilization）**



Decode阶段的性能几乎完全受制于HBM带宽。以H100为例，其理论HBM带宽为3.35TB/s，但实际推理中由于KV Cache读取的随机性和非连续性，利用率通常在40%-60%。提升显存带宽利用率是优化TPOT的直接路径。



**综合评估框架**：一流的AI Infra团队会构建**推理成本仪表盘**，同时追踪：



* **边际成本/Token**：每新增一个Token的推理成本

* **GPU小时产出**：每GPU小时处理的Token数

* **空闲周期占比**：GPU等待数据的时间占比

## 指标全景图：从业务到系统的映射

为便于记忆和理解，我们将本课所有指标整合到一张**层次化全景图**中：



| 层次        | 指标                      | 核心问题     | 典型优化手段                   |
| --------- | ----------------------- | -------- | ------------------------ |
| **用户体验层** | TTFT、TPOT、E2E延迟         | 用户爽不爽？   | PD分离、FlashAttention、投机解码 |
| **系统效率层** | Tokens/s、Requests/s、MFU | 资源用得足不足？ | 连续批处理、动态Batching         |
| **服务质量层** | P99延迟、SLO达标率、错误率        | 系统稳不稳？   | 调度优化、弹性扩缩容、可观测性          |
| **商业价值层** | 每百万Token成本、GPU利用率       | 能不能赚钱？   | 模型压缩、KV Cache量化、架构选型     |





这四个层次由浅入深、层层递进。一个优秀的推理优化方案，必须在这四个层次上都能交出令人信服的答卷。

## 引言：从“每次只能走一步”到“一次跨越数步”

自回归生成是大模型推理的根本瓶颈——每次只能生成一个Token，每个Token都要走一遍完整的模型前向传播。在这个过程中，**内存带宽墙**成为主要限制：H100的算力高达990 TFLOPS，但内存带宽只有3.35 TB/s，自回归解码时，GPU大部分时间都在等待从显存搬运数据，真正用于计算的周期占比很低。



这就引出一个自然的问题：既然读取一次模型权重很昂贵，能不能让它一次读取、验证多个Token？



投机解码（Speculative Decoding）正是基于这个朴素想法诞生的技术。它的核心思路与CPU的分支预测异曲同工——**用一个轻量级的草稿模型快速猜测接下来的若干Token，然后用大模型一次性验证这些猜测是否正确**。如果猜对了大部分，那就相当于用一次大模型前向传播换来了多个Token的生成，推理速度由此倍增。





## 一、投机解码的核心原理

### 1.1 从“一次一个”到“一次验证一串”

投机解码的本质是 **“草稿-验证”（Draft-then-Verify）** 的解码范式。每一轮迭代包含三个步骤：



**第一步：草稿生成（Drafting）**



一个小型草稿模型（比如Llama-3.2-1B）以自回归方式快速生成K个候选Token。由于草稿模型参数少、计算量小，单Token生成速度比大模型快一个数量级（通常约10倍）。



**第二步：并行验证（Verification）**



目标大模型（如Llama-3.1-70B）在一次前向传播中**同时处理全部K个草稿Token**。验证是并行的——目标模型为每个位置计算下一个Token的概率分布，一次前向传播完成K个Token的校验，而自回归方式需要K次。



**第三步：接受或拒绝（Accept/Reject）**



逐个比较草稿模型与目标模型给出的概率分布：一致的则接受，不一致的则拒绝并从目标模型在该位置的分布中重新采样，同时丢弃后续所有草稿Token。



整个流程有一个数学上严格的保证：**输出分布与目标模型独立运行时完全一致**。不是近似，而是严格相同——这意味着投机解码是**无损加速**，不会带来任何质量损失。



### 1.2 加速效果的关键：接受率

假设草稿模型每次提出5个候选Token（K=5），接受率为80%，那么每次验证平均接受4个Token，大模型的前向传播开销降为原来的四分之一。需要注意的是，实际端到端加速效果还要考虑草稿模型自身的计算开销，真实场景下的加速比通常为2-2.5倍。



### 1.3 投机解码与“内存墙”

投机解码之所以能有效加速，根本原因在于它改变了推理的计算特征。**自回归解码是内存带宽受限的**——每生成一个Token就要从HBM读取一遍模型权重，即使算力再强，也要等数据搬运。而验证阶段是**计算受限的**——一次前向传播处理多个Token，可以更充分地利用Tensor Core的计算能力。投机解码的本质，就是把“内存带宽受限的解码”转化为“计算受限的并行验证”，从而绕过内存墙的束缚。







## 二、草稿模型的选择与训练

草稿模型的设计直接影响接受率和加速效果，是投机解码工程化的核心决策。随着技术的发展，草稿模型的设计经历了从独立模型到自生成模型的演进。



### 2.1 独立草稿模型（Independent Drafting）

最经典的方式是使用一个与目标模型**同系列的小型语言模型**作为草稿生成器。例如，用Llama-3.2-1B作为Llama-3.1-70B的草稿模型。



**优势**：推理延时低、可针对性优化、资源占用可控。



**局限**：



* **分布不匹配**：如果草稿模型与目标模型训练数据分布或能力存在差异，接受率会大幅下降。

* **额外的显存开销**：两个模型同时驻留显存，对显存容量提出更高要求。

* **分词器必须兼容**：标准辅助生成要求两个模型使用相同的分词器，意味着必须来自同一模型系列。

针对分词器不兼容的痛点，Hugging Face与英特尔研究院合作开发了**通用辅助生成（Universal Assisted Generation, UAG）** 技术，通过双路分词器映射，允许任意搭配目标模型和辅助模型。



### 2.2 自草稿生成（Self-Drafting）

为了规避独立草稿模型的局限，学术界发展出了“自草稿生成”方案——**不引入额外模型，而是从目标模型自身挖掘草稿能力**。



这类方案的核心思路是：既然目标模型的前几层已经提取了丰富的特征表示，能否用**轻量级的额外预测头**直接从中间层预测后续Token？



**Medusa**：在目标模型的隐藏层上添加多个预测头（Prediction Heads），每个头负责预测未来一个特定位置的Token。例如，第一个头预测第t+1个Token，第二个头预测第t+2个Token……这样，一次前向传播就能同时获得多个未来位置的候选Token。



**EAGLE系列（EAGLE-2/EAGLE-3）** ：进一步优化了自草稿生成的架构，利用目标模型的隐藏状态进行更准确的草稿预测。EAGLE-3已被集成到vLLM生态的Speculators库中，支持端到端的训练和部署。



自草稿生成的最大优势是**无需在显存中同时维护两个模型**，并且草稿质量与目标模型更“对齐”，接受率通常更高。缺点是需要在目标模型上额外训练预测头（虽然训练量相对较小）。







## 三、投机解码的性能收益分析

### 3.1 场景敏感性

投机解码的加速效果高度依赖**场景特性**，并非“一招鲜吃遍天”：



| 场景类型            | 接受率     | 加速效果   |
| --------------- | ------- | ------ |
| 代码生成、数学推理（确定性强） | 70%-85% | 接近理论上限 |
| 创意写作、对话闲聊（分布平滑） | 30%-40% | 效果大打折扣 |





在代码和文本编辑任务中，LMCache Lab的实测显示投机解码可将Token生成时间降低**60%**。这类任务的特点是经常复用已有的词组，草稿模型更容易猜中。而在高温度采样或创意生成场景中，目标模型自身的分布也比较平坦，草稿模型的猜测更容易被拒绝。



### 3.2 与其他优化技术的协同

投机解码并非孤立技术——它与KV Cache压缩、连续批处理等优化手段组合使用时能产生**乘数效应**：



* 投机解码**降低每Token的计算量与延迟**

* KV Cache压缩**提升单卡并发能力**

2026年主流推理平台的推荐配置是：**GQA架构模型 + 4-bit KV Cache量化 + 自适应投机解码**。实测显示，在Llama-3-70B上，每卡每秒可处理超过200个生成Token，单卡并发用户数从基线配置的4-8人提升至30-50人，推理成本降至原来的六分之一。



### 3.3 硬件与工程限制

投机解码在生产环境中也面临一些约束：



* **小Batch场景收益更明显**：当Batch已经饱和时，投机解码的边际收益会下降。

* **草稿模型不能太小**：一般来说，辅助模型需要至少比目标模型小50-100倍才会看到有意义的加速。

* **交互式场景优先**：投机解码对降低首Token延迟的帮助有限，其最大价值在于降低Token间延迟（TPOT）。

## 四、变种技术：Lookahead Decoding与Medusa

### 4.1 Medusa：多头预测

Medusa的核心创新是在目标模型的隐藏层上**添加多个额外的预测头**，每个头专门预测未来一个特定位置的Token，而不需要独立的草稿模型。其架构可以这样理解：



```plain&#x20;text
输入 → 目标模型（冻结）→ 隐藏状态
                          ├── 原始头 → 预测 t+1
                          ├── Medusa头1 → 预测 t+2
                          ├── Medusa头2 → 预测 t+3
                          └── Medusa头3 → 预测 t+4
```



训练分为两个版本：



* **Medusa-1**：冻结目标模型，只训练预测头，可实现约2.2倍加速，输出无损

* **Medusa-2**：将目标模型与预测头一起微调，可实现2.3-3.6倍加速，但需要更复杂的训练流程

Medusa还利用**树形注意力（Tree-based Attention）** ——在一个前向传播中验证一棵候选树的所有分支，而非单一的线性序列。



### 4.2 Lookahead Decoding：无需训练的并行猜测

Lookahead Decoding（前瞻解码）走了一条不同的路径——**不依赖任何草稿模型**，而是利用**雅可比迭代（Jacobi Iteration）** 并行求解多个未来Token。



**核心思路**：将自回归解码重新表述为求解一个方程组，然后用雅可比迭代法并行求解，而非逐个求解。



**工作流程**：



1. **Lookahead分支**：并行生成N-gram候选（W×N个候选）

2. **验证分支**：验证那些看起来有希望的N-gram，匹配成功则接受

Lookahead Decoding不依赖训练，部署简单，加速效果约为**1.3-1.6倍**。当没有合适的草稿模型、也缺乏微调预算时，它是一个实用的备选方案。



### 4.3 选型速查

| 方案        | 是否需要训练    | 是否需要额外模型 | 典型加速比    | 适用场景        |
| --------- | --------- | -------- | -------- | ----------- |
| 独立草稿模型    | 否         | 是（小型模型）  | 2-2.5×   | 存在同系列小模型    |
| Medusa    | 是（仅训练头）   | 否        | 2.2-3.6× | 有微调预算，无额外显存 |
| EAGLE     | 是（基于隐藏状态） | 否        | 2-3×     | 追求最高接受率     |
| Lookahead | 否         | 否        | 1.3-1.6× | 无训练预算，快速部署  |
